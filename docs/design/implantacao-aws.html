Implantação AWS do Auditor

Recomendação de arquitetura para o Auditor em produção: Frontend em CloudFront + S3, API e Worker como funções AWS Lambda atrás de um Application Load Balancer, RDS PostgreSQL Multi-AZ com pgvector, fila SQS e Parameter Store. Ollama continua em EC2 por decisão própria (ADR-0013), não por limitação de conta.

Por que Lambda, e não ECS/EC2: o Auditor é uma ferramenta de baixo tráfego, de uso esporádico — o perfil clássico onde pagar por invocação bate um serviço sempre ligado. API e Worker escalam a zero fora de uso (custo de compute ≈ R$0 quando ninguém audita) e o ALB aponta direto para a Lambda da API, sem precisar de API Gateway. Ver o card "Compute" para as alternativas descartadas e por quê.

Entrega do Frontend

CloudFront · S3 · Route 53
  • Bucket S3 privado com o build de produção (ng build), sem acesso público direto.
  • CloudFront na frente do bucket via Origin Access Control (OAC), com HTTPS, cache de borda e domínio próprio via Route 53 + ACM.
  • Chamadas de API vão direto ao ALB — este desenho não coloca a API atrás do CloudFront.

Rede & Segurança

VPC · 2 AZs
  • 1 VPC, subnets públicas (ALB, NAT) e privadas (compute, dados) replicadas em 2 AZs para alta disponibilidade real.
  • Security groups encadeados por camada, nunca um único SG compartilhado: sg-alb abre 443 ao mundo; sg-lambda (API e Worker) só aceita do sg-alb/do serviço SQS; sg-ollama-ec2 e sg-rds só aceitam do sg-lambda — cada referência é a outro SG, nunca um CIDR aberto.
  • VPC Interface Endpoints (PrivateLink) dedicados para SQS e Parameter Store — as chamadas de API/Worker a esses serviços nunca saem da rede da AWS. Isso libera o NAT Gateway para a única saída realmente externa: Worker → Orion do cliente, fora da AWS.

Compute

AWS Lambda (API + Worker) · EC2 (Ollama)
  • API e Worker como Lambda, anexadas à VPC: a API roda o mesmo FastAPI de hoje atrás de um adapter Mangum, alvo direto do ALB (sem API Gateway); o Worker é invocado pelo event source mapping nativo do SQS, reaproveitando o RunAuditUseCase sem tocar a lógica de negócio.
  • Por que não ECS Fargate: Fargate cobra por vCPU/memória-segundo mesmo com poucas requisições — para um app de baixo tráfego, isso é custo ocioso. Zerar o desired_count por agenda economiza, mas não acorda sozinho quando alguém acessa (a requisição cai em 503 até alguém religar). Lambda entrega esse "liga sob demanda" nativamente.
  • Por que não EC2 direto (estado atual do Terraform): 2 instâncias rodando 24/7 só para API/Worker, cobrando parado — o pior caso de custo ocioso para esse perfil de uso.
  • Ollama continua em EC2 t3.large (CPU, sem GPU) rodando Qwen2.5 3B/4B, always-on — decisão própria (ADR-0013), não uma limitação de conta, e não depende de qual compute a API/Worker usam: um LLM residente em memória não é candidato a serverless.
  • Trade-off aceito: cold start na primeira requisição após ociosidade (centenas de ms a poucos segundos) — aceitável para uma ferramenta interna de auditoria; mitigável com Provisioned Concurrency se algum dia incomodar.

Dados & Filas

RDS · SQS · Parameter Store
  • RDS PostgreSQL Multi-AZ com a extensão pgvector (criada pela migration Alembic) para o catálogo semântico e o RAG do SLM.
  • Fila audit-jobs + DLQ audit-jobs-dlq com redrive policy — mesmo contrato de hoje, só que consumida por invocação em vez de polling manual.
  • Parameter Store (SecureString, tier standard) guarda credenciais do Orion do cliente e a chave de assinatura JWT — mesma criptografia via KMS do Secrets Manager, sem o custo de $0,40/segredo/mês; só abre mão da rotação automática nativa, que este projeto não usa hoje.
