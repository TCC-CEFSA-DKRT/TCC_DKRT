# ADR-0020: Sessão por cookie httpOnly (SaaS) + gate de Configuração (self-hosted) + `/session` em runtime no lugar da flag de build

Data: 2026-09-27

Status: Proposto

## Contexto

A ADR-0019 decidiu os dois modos de implantação e já implementou o backend de autenticação
(`POST /auth/login`, JWT, `deployment_mode`) — mas o frontend nunca ganhou tela de login nem tela
de Configuração, e duas premissas da própria ADR-0019 não correspondem ao código: a linha 62 diz
que o self-hosted lê o tenant de `Settings.fiware_service`, mas o runtime (`get_context_broker`)
sempre usava `OrionAdapter(settings.fiware_broker_url, ...)` direto — a tabela `tenant_accounts`
nunca era lida em modo self-hosted, então gravar uma configuração pela UI não teria efeito
nenhum. A linha 108 cita uma flag de build `environment.selfHosted` que nunca existiu:
`frontend/src/environments/` e `fileReplacements` no `angular.json` nunca foram criados. Fechar o
login (SaaS) e o gate de Configuração (self-hosted) — o produtor não consegue avançar sem
configurar o broker — exige decidir como o frontend guarda a sessão e como o runtime do backend
descobre "estou configurado?" nos dois modos, sem reintroduzir a mesma divergência ADR-vs-código.

## Decisão

- **Sessão do SaaS é um cookie `httpOnly`, não `localStorage`.** `POST /auth/login` devolve
  `Set-Cookie: auditor_session=<jwt>` com `HttpOnly`, `Secure` (sempre, sem flag de desligar),
  `SameSite=Strict`, `Path=/`, `Max-Age` igual ao `exp` do JWT (`jwt_expiration_minutes * 60`), e
  **sem `Domain`** (cookie host-only). O corpo da resposta continua trazendo o JWT também
  (`access_token`), para clientes não-navegador (curl, scripts, `test_b11_real_round_trip_...`)
  continuarem usando `Authorization: Bearer` sem mudança.
- **`GET /session`, sempre montado, nunca 401.** Substitui a flag de build
  `environment.selfHosted` citada (e nunca implementada) na ADR-0019: em vez de a build do
  frontend decidir estaticamente se existe tela de login, o mesmo bundle pergunta ao backend em
  runtime `{deployment_mode, tenant}`. Em `saas`, decodifica o cookie/Bearer recebido e devolve
  `tenant=null` sem erro se não houver sessão válida (nunca 401 — é uma sonda). Em `selfhosted`,
  devolve o tenant salvo em `tenant_accounts` (ou o de `Settings.fiware_service*` quando não há
  chave Fernet configurada), ou `null` quando não há nada configurado — isso é o que aciona o
  gate de Configuração no frontend.
- **Gate de Configuração no self-hosted.** `GET`/`PUT /config`, montado só em `deployment_mode
  != "saas"` (espelho de `auth`, que só existe em `saas`). Antes desta decisão, o runtime do
  self-hosted nunca lia `tenant_accounts` — `SelfHostedContextBroker` (novo, estende
  `TenantRoutedContextBroker` só trocando `_adapter_for` para ignorar o tenant recebido e usar
  `TenantAccountRepository.get_single()`) fecha essa lacuna: com uma linha salva, usa
  `broker_url`/`broker_api_key` dela; sem linha, cai no `Settings.fiware_broker_url` de sempre —
  preserva `run_experiment.py`, o e2e e `audit run --tenant X`, que continuam endereçando
  qualquer tenant no mesmo Orion.
- **`broker_api_key` fica fora do formulário/endpoint `/config`.** `PUT /config` sempre grava
  `broker_api_key=None` (via `create` quando não há linha, `replace_tenant` quando há — DELETE +
  INSERT atômico, como a ADR-0019 já previa). **Consequência aceita e documentada aqui:** se um
  produtor cadastrou uma `api_key` por `audit tenant register --broker-api-key`, salvar a
  configuração pela UI depois **apaga essa chave** (fica `None`). Preservar a chave antiga ao
  salvar pela UI foi descartado (ver Alternativas) porque, se `broker_url` mudar no mesmo save, a
  chave vazaria para um host diferente do que a autorizou — pior que exigir reentrada.
- **Sem `SESSION_COOKIE_SECURE`.** `Secure` fica fixo em `True` no código (não é uma env var).
  Chrome trata `http://localhost` como contexto seguro para cookies `Secure`, então o dev SaaS em
  `localhost:4200 → localhost:8000` funciona sem exceção. Um flag desligável em produção seria uma
  armadilha (fácil esquecer religado). Risco aceito e documentado: em Safari ou num IP de LAN
  (não `localhost`), o cookie `Secure` via `http://` é descartado pelo navegador e a app entra em
  loop no `/login` — mitigação é usar `localhost` no dev, não uma flag de config.
- **Guarda de CORS `"*"` em `saas`.** `Settings` ganha um `model_validator` que rejeita
  `cors_allowed_origins_list == ["*"]` (ou contendo `"*"`) quando `deployment_mode == "saas"`. O
  Starlette 1.0.0 instalado reflete qualquer `Origin` quando `allow_origins=["*"]` e
  `allow_credentials=True` — com autenticação por cookie, isso equivale a desligar CORS de fato.
  Nada define `"*"` hoje em produção, mas a partir desta decisão (cookie com `allow_credentials`)
  isso passa a ser um erro de configuração fail-fast, não um risco silencioso.
- **Bug independente corrigido:** `selfhosted/docker-compose.yml` (serviço `app`) não definia
  `CORS_ALLOWED_ORIGINS`, então valia o default `http://localhost:4200` — mas o frontend do bundle
  roda em `:5173`. Passa a definir `CORS_ALLOWED_ORIGINS: http://localhost:5173`.

## Alternativas consideradas

- **`localStorage` para o JWT** — descartada: qualquer XSS na aplicação consegue ler o token
  inteiro e reutilizá-lo fora da sessão do navegador (ex.: exfiltrar e usar de outra máquina). Um
  cookie `httpOnly` não pode ser lido por JavaScript nenhum, então um XSS só age *dentro* da
  página logada, sem poder levar o token para fora.
- **Cookie legível por JavaScript (sem `HttpOnly`)** — descartada: perderia exatamente a
  propriedade acima (o motivo de usar cookie em vez de `localStorage`) sem ganhar nada em troca;
  o frontend não precisa ler o valor do token, só saber "estou logado" via `GET /session`.
- **`Domain=<domínio raiz>` no cookie** — descartada: um cookie host-only definido por `api.X` já
  é enviado em XHR com credenciais partindo de `app.X`, porque os dois são *same-site* (mesmo
  eTLD+1). Com `Domain=` na raiz, o JWT passaria a ser enviado a **todos** os subdomínios de `X`,
  ampliando a superfície de um XSS ou de um subdomínio comprometido sem necessidade nenhuma —
  a API nunca precisa do cookie fora de si mesma.
- **`SESSION_COOKIE_SECURE` configurável (default `True`)** — descartada por ora: um flag
  desligável em produção é fácil de deixar religado por engano (aí o cookie de sessão viaja em
  texto claro). Fica registrada como evolução se o dev em Safari/LAN via `http://` se mostrar
  necessário na prática.
- **Preservar `broker_api_key` antiga ao salvar `/config` pela UI** — descartada: exigiria um
  input write-only ("deixe em branco para manter") mais um repasse explícito no `PUT`, e ainda
  assim, se `broker_url` mudar no mesmo save, a chave antiga vazaria para o host novo sem o
  produtor ter pedido isso. Mais simples e mais seguro exigir reentrada via CLI
  (`audit tenant register --broker-api-key`) quando o broker exigir chave.

## Consequências

**Positivas:**
- Fecha a divergência real entre a ADR-0019 e o código: o self-hosted passa a ler de fato
  `tenant_accounts` via `SelfHostedContextBroker`, e `/session` substitui a flag de build que
  nunca chegou a existir — uma única build do frontend serve os dois modos.
- O cookie `httpOnly` + `GET /session` cobre login, "estou logado?" após F5, e o gate de
  Configuração com uma única sonda barata (sempre 200), sem precisar de `/auth/me` separado.
- O guard de CORS `"*"` em `saas` transforma um risco de configuração silencioso (reflexão de
  qualquer `Origin` com credenciais) em falha rápida no boot.

**Negativas / trade-offs aceitos:**
- Salvar a configuração pela UI self-hosted apaga qualquer `broker_api_key` cadastrada
  previamente via CLI — documentado aqui, não impedido no código; o produtor precisa recadastrar
  a chave por `audit tenant register --broker-api-key` depois de usar a UI, se o broker exigir.
- Sem `SESSION_COOKIE_SECURE`, o dev SaaS fora de `localhost` (Safari, IP de LAN) não funciona sem
  ajuste manual — aceito por ora, documentado como limitação conhecida do ambiente de
  desenvolvimento, não de produção.
- O JWT continua sem revogação no servidor (stateless, como já era desde a ADR-0019): um token
  vazado (do corpo da resposta de login, ou do próprio cookie via XSS dentro da página) vale até
  o `exp`, no máximo `jwt_expiration_minutes` (default 60). `POST /auth/logout` apaga o cookie do
  navegador, mas não invalida o JWT em si.
