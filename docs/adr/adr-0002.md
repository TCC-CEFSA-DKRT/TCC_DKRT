# ADR-0002: Loop de execução com verificação determinística e correção

Data: 2026-08-09
Status: Aceito

## Contexto

O comportamento desejado do produto vai além de "executar comando e reportar sucesso/erro": ao criar uma entidade (ex.: registrar um sensor), o sistema deve confirmar que os dados foram gravados corretamente, e, em caso de erro, tentar corrigir automaticamente ou pedir esclarecimento ao usuário antes de desistir. A primeira formulação dessa ideia cogitava um agente autônomo próprio para cada operação (create, update, delete, subscribe, analyze), cada um capaz de raciocinar e se auto-corrigir de forma independente — o que multiplicaria chamadas ao SLM local a cada operação, um risco real de latência e de divergência da intenção original com um modelo pequeno (Qwen2.5 via Ollama, local).

## Decisão

Adotar o padrão **ReAct** (Reasoning + Acting): um único ponto de decisão via SLM que age, observa o resultado real da ação executada, e decide o próximo passo com base nessa observação — em vez de múltiplos agentes autônomos independentes.

Fluxo:
1. SLM classifica a intenção e extrai parâmetros (JSON estruturado).
2. Código determinístico executa a ação no FIWARE.
3. Código determinístico **verifica** o resultado — re-consulta a entidade e compara campo a campo com o que foi solicitado. Este passo nunca é delegado ao SLM.
4. Se bateu: confirma ao usuário. Se não bateu: classifica o tipo de erro e decide, de forma determinística, entre corrigir automaticamente (retry limitado a 2–3 tentativas) ou pausar e perguntar ao usuário, guardando o estado parcial da operação.

## Alternativas consideradas

- **Múltiplos agentes autônomos, cada um com seu próprio ciclo de raciocínio via SLM** — descartada: cada chamada adicional ao SLM é um ponto de falha a mais para um modelo pequeno local; o custo de latência (múltiplas chamadas Ollama por operação) também é proibitivo para uma CLI interativa.
- **Verificação via SLM** (pedir ao modelo para "julgar" se o resultado da consulta bate com o que foi pedido) — descartada: comparação de dados estruturados é tarefa determinística; delegar isso ao SLM introduz risco de alucinação (o modelo pode concluir que os dados batem quando não batem) sem nenhum ganho sobre um diff de código.
- **Sem loop de correção, apenas reportar erro bruto ao usuário** — descartada: não atende ao caso de uso central do produto (interação robusta em linguagem natural), e desperdiça a oportunidade de recuperação automática em erros simples e comuns (tipo de atributo incorreto, campo obrigatório inferível pelo contexto).

## Consequências

**Positivas:**
- Uso do SLM concentrado e previsível: uma chamada para classificar, e (só quando necessário) uma chamada adicional para interpretar um erro — não um número variável e potencialmente alto de chamadas por operação.
- Verificação confiável, porque não depende da capacidade de julgamento de um modelo pequeno.
- Experiência mais próxima da de um "desenvolvedor FIWARE assistente" real, que confere o próprio trabalho.

**Negativas / trade-offs aceitos:**
- Mais latência por operação bem-sucedida (uma consulta extra de verificação sempre acontece, mesmo quando tudo deu certo na primeira tentativa) — aceito como custo de confiabilidade.
- Exige definir e manter uma taxonomia de erros (corrigível automaticamente vs. precisa do usuário) por tipo de operação, o que é trabalho de engenharia adicional, não só de prompt.
