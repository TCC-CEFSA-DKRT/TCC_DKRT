# ADR-0012: IoT Agent MQTT como sétima operação do vocabulário (iot_provision)

Data: 2026-08-16
Status: Aceito

## Contexto

A ADR-0004 definiu "cobertura completa do backend de referência" como
Orion + IoT Agent MQTT + QuantumLeap + bancos associados, mas até este
momento o IoT Agent nunca foi implementado — o vocabulário de operações
(ADR-0001) tinha seis itens (`query, list, create, update, delete,
subscribe`), nenhum deles cobrindo provisionamento de dispositivo.

Provisionar um dispositivo no IoT Agent não é o mesmo que `create`: o
`CreateHandler` cria uma entidade NGSI diretamente no Orion; provisionar um
dispositivo registra-o no IoT Agent (`POST /iot/services` +
`POST /iot/devices`), que passa a criar/atualizar a entidade no Orion por
conta própria quando o dispositivo físico publica uma medida via MQTT. São
APIs e semânticas diferentes — tratar como a mesma operação confundiria o
propósito de cada uma.

## Decisão

Adicionar `iot_provision` como sétima operação do vocabulário oficial
(`agents/registry.py`, `models/intent.Operation`), com um handler próprio
(`IoTProvisionHandler`) e um cliente dedicado (`IoTAgentClient`,
`services/iot_agent_client.py`) para a API do IoT Agent (porta 4041 por
padrão). `iot_provision` entra em `MUTATION_OPERATIONS`: passa pelo mesmo
loop de verificação do ADR-0002 (reconsulta `GET /iot/devices/{id}` para
confirmar o registro antes de considerar concluído).

`docker-compose.yml` ganha os serviços `mosquitto` (broker MQTT) e
`iot-agent-mqtt` (imagem `fiware/iotagent-json`, transporte MQTT).

## Alternativas consideradas

- **Reaproveitar a operação `create` para provisionamento de dispositivo**
  — descartada: são duas APIs com formatos de payload e endpoints
  completamente diferentes (entidade NGSI vs. registro de dispositivo);
  forçar as duas sob o mesmo rótulo exigiria o handler inspecionar o
  payload para decidir "isso é entidade ou é dispositivo?", reintroduzindo
  o tipo de ambiguidade que a ADR-0001 eliminou ao separar operações.

## Consequências

**Positivas:**
- O backend de referência da ADR-0004 (Orion + IoT Agent + QuantumLeap)
  fica coberto pelo mesmo padrão arquitetural das demais operações —
  classificação por SLM/fallback, execução determinística, verificação
  obrigatória.
- Nenhuma mudança foi necessária em `ActionExecutor`, `ChatEngine` ou
  `AnalyzeHandler`: o padrão Registry (ADR-0001) absorveu a operação nova
  sem exigir alterações fora de `agents/`, `core/intent_router.py` e do
  prompt/fallback de classificação.

**Negativas / trade-offs aceitos:**
- O prompt do SLM (`CHAT_ANALYSIS_PROMPT`) e a heurística de fallback
  (`RouteDispatcher.classify`) precisaram de ajuste manual para reconhecer
  a operação nova — é o próprio limite documentado na ADR-0000: adicionar
  capacidade ainda exige mudança de código, não só de documentação.
- Corrigido de passagem: a validação de operação em
  `SLMService._parse_chat_analysis` não incluía `subscribe` na lista de
  operações aceitas (bug pré-existente, anterior a esta ADR) — corrigido
  junto por estar no mesmo bloco de código.
