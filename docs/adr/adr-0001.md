# ADR-0001: Unificação da arquitetura de agentes

Data: 2026-08-09
Status: Aceito

## Contexto

O projeto evoluiu em fases distintas do TCC e acumulou **duas implementações paralelas** do mesmo domínio (interação com o Context Broker), que nunca se comunicam entre si:

- `orchestrator.py` (`MultiAgentOrchestrator`) executa todos os agentes (`RouteAgent`, `QueryAgent`, `SubscribeAgent`, `ProvisionAgent`, `AnalyzeAgent`) em paralelo via `asyncio.gather`, sempre — usado pelos comandos `dkrt ask`/`dkrt orchestrate`.
- `core/chat_engine.py` + `core/intent_router.py` usam um segundo conjunto (`QueryAgent`, `ListAgent`, `CreateAgent`, `UpdateAgent`, `DeleteAgent`), escolhendo um só com base na intenção decidida pelo SLM — usado pelo terminal interativo (`dkrt`), o fluxo principal do produto.

O mapeamento código a código confirmou que a sobreposição é quase total: `ProvisionAgent` duplica exatamente o que `CreateAgent` faz (ambos montam `NgsiEntity` e chamam `create_entity`); `QueryAgent` já é compartilhado pelos dois sistemas; `SubscribeAgent` está incompleto (monta o plano de subscrição mas nunca o envia ao Orion); `RouteAgent` classifica intenção por palavra-chave, sem usar o SLM; `AnalyzeAgent` não executa nenhuma operação NGSI própria — apenas sumariza dados já buscados por outro agente.

## Decisão

Consolidar em uma única arquitetura de agentes, registrada em um `agents/registry.py` central (padrão Command/Strategy Registry), usada por **todos** os pontos de entrada (terminal, `dkrt ask`, `dkrt orchestrate`, e futuramente o servidor MCP):

- Vocabulário único de operações: `list`, `query`, `create`, `update`, `delete`, `subscribe`, `analyze`, mais `history` (ver ADR-0003/Bloco 5).
- `ProvisionAgent` é eliminado (redundante com `CreateAgent`).
- `AnalyzeAgent` deixa de ser uma operação independente e passa a ser um passo de pós-processamento opcional após `QueryAgent`, não um agente com rota própria.
- `RouteAgent`, como classificador por palavra-chave, é mantido apenas como *fallback* determinístico caso o SLM esteja indisponível — não como via principal de decisão.
- `MultiAgentOrchestrator` (execução paralela incondicional de todos os agentes) é removido do caminho de decisão principal; `IntentRouter` passa a ser o único despachante, escolhendo um agente por vez com base na intenção classificada pelo SLM.

## Alternativas consideradas

- **Manter os dois sistemas e apenas documentar quando usar cada um** — descartada: perpetua a inconsistência e viola o princípio de fonte única da verdade; qualquer correção futura teria que ser replicada em dois lugares.
- **Migrar tudo para o modelo do `orchestrator.py` (paralelo, sempre roda todos os agentes)** — descartada: mais lento (todo comando dispara 5 chamadas, mesmo quando só uma é relevante) e semanticamente errado (rodar `DeleteAgent` numa consulta simples não faz sentido).

## Consequências

**Positivas:**
- Uma única fonte de verdade para decisão de agente; correções e testes cobrem todos os entrypoints de uma vez.
- Redução de complexidade: de 10 arquivos de agente para ~7, sem perda de funcionalidade real.
- Base pronta para receber os novos agentes do Bloco 5 (`HistoryAgent`, IoT Agent) sem criar uma terceira ramificação paralela.

**Negativas / trade-offs aceitos:**
- Perde-se a paralelização "roda tudo de uma vez" do `orchestrator.py` — aceitável, porque essa paralelização não correspondia a um ganho real (a maioria das operações é mutuamente exclusiva: uma mensagem do usuário raramente pede `create` e `delete` ao mesmo tempo).
- Exige reescrever os testes que cobriam o `orchestrator.py` isoladamente.
