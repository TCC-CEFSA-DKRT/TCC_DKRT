# ADR-0013: Ollama em EC2 (não Bedrock) como SLM de produção

Data: 2026-09-06
Status: Aceito (tipo de instância revisto pela ADR-0015 — a decisão Ollama-vs-Bedrock
abaixo permanece válida; só o dimensionamento sem GPU mudou)

## Contexto

A Fase 9 (`.cursor/specs/fase9.spec.md`, seção 6) pedia uma decisão
fundamentada entre duas formas de servir o SLM em produção na AWS Academy
Learner Lab: Amazon Bedrock (modelo gerenciado, cobrança por token) ou
Ollama numa instância EC2 (modelo self-hosted, cobrança por hora de
instância ligada). O spec original pedia essa decisão apoiada numa
comparação de custo usando o orçamento real restante da conta Academy do
usuário.

Ao ser perguntado sobre isso, o usuário respondeu que já havia decidido
antes da pergunta: *"Eu pensei em usar o ollama com um modelo SLM como o
qwen 3b 4b ou etc, não disse nada sobre bedrock"*. Ou seja, a decisão não
resulta de uma comparação de custo formal entre as duas opções — o Bedrock
nunca esteve em consideração pelo usuário. Registrar isso honestamente é
mais fiel ao processo real do que fabricar uma comparação retroativa com
números de Bedrock que ninguém pesou.

## Decisão

Servir o SLM em produção via **Ollama numa instância EC2**, com um modelo
pequeno (Qwen 2.5 3B ou 4B, ou equivalente) — decisão direta do usuário,
não uma escolha derivada de análise de custo Bedrock-vs-EC2 feita nesta
sessão.

Tecnicamente, isso não exige nenhuma mudança de código de aplicação:
`get_semantic_analyzer()` (`src/auditor/infrastructure/config/container.py`)
já instancia `OllamaAnalyzer` a partir de `Settings.ollama_base_url` /
`ollama_model` — `BedrockAnalyzer`
(`src/auditor/infrastructure/llm/bedrock_analyzer.py`) existe como
implementação alternativa da mesma porta (`SemanticAnalyzerPort`), mas não
está e não precisa estar conectada. Apontar `OLLAMA_BASE_URL` para o IP
privado da instância Ollama (resolvido automaticamente pelo módulo
Terraform `infra/terraform/modules/compute`, via `user_data`) é suficiente.

Um SLM de 3B/4B parâmetros roda em CPU sem GPU — `modules/compute` usa
`t3.large` (8 GiB RAM) como instância default para o Ollama, não uma
instância com GPU. Como `aws_instance` não tem um argumento de "estado
desejado" no Terraform (só existe ou não existe), a instância Ollama nunca
fica ligada por padrão: seu ciclo ligado/desligado é controlado
explicitamente pelos scripts
`infra/terraform/environments/academy/scripts/start_ollama.sh` e
`stop_ollama.sh`, fora do `apply`/`destroy`.

## Alternativas consideradas

- **Amazon Bedrock** — descartada, mas não por uma comparação de custo
  real feita nesta sessão: o usuário simplesmente nunca considerou essa
  opção. Uma comparação de custo genuína exigiria o preço por token de um
  modelo Bedrock equivalente e o orçamento real restante da conta Academy
  do usuário — nenhum dos dois estava disponível nesta sessão de trabalho,
  e fabricar números para preencher essa lacuna produziria uma justificativa
  sem lastro, pior do que documentar a decisão como ela realmente foi
  tomada.

## Consequências

**Positivas:**
- Nenhuma mudança de código de aplicação necessária — `BedrockAnalyzer`
  permanece no código como implementação alternativa não utilizada, útil
  se esta decisão for revisada no futuro.
- Custo de instância relativamente baixo para um SLM pequeno em CPU
  (`t3.large`, sem GPU) — mas o valor exato em USD/hora deve ser conferido
  na calculadora de preços da AWS para `us-east-1` no momento do uso, já
  que preços mudam e este ADR não fixa um número que ficaria desatualizado.

**Negativas / trade-offs aceitos:**
- Exige disciplina manual de start/stop (`start_ollama.sh` antes de um
  experimento, `stop_ollama.sh` depois — ver Fase 10) para não consumir
  crédito da Academy com a instância ociosa; o Bedrock não teria esse
  custo de infraestrutura parada.
- Se o volume de uso crescer a ponto de a instância precisar ficar ligada
  quase o tempo todo, esta decisão deveria ser revisitada com uma
  comparação de custo real contra Bedrock — o que não foi feito aqui.

## Nota de revisão (2026-09-09)

A ADR-0014 mudou quando o Nível 2 (SLM) é acionado: de "só ~10% das entidades, as que o
Nível 1 já reprovou" para "toda entidade com schema resolvido". Isso multiplica por ~10x o
volume de chamadas de inferência por auditoria, o que tornou o dimensionamento sem GPU
deste ADR (`t3.large`) desatualizado para esse novo volume — ver **ADR-0015**, que troca a
instância do Ollama para `g4dn.xlarge` (GPU). A decisão Ollama-em-EC2-e-não-Bedrock feita
aqui não muda; só o tipo de instância.
