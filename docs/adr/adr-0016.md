# ADR-0016: Servidor MCP como adaptador de entrada para expor a auditoria a clientes de IA

Data: 2026-09-10
Status: Aceito

## Contexto

Ao perguntar sobre o Model Context Protocol (MCP) — tecnologia recorrente em artigos
recentes — o usuário propôs uma hipótese específica: usar MCP para "adaptar o protocolo
NGSI para que o SLM entenda melhor as entidades". Investigar essa hipótese revelou uma
confusão de papel que precisa ficar registrada, porque orienta onde o MCP entra (e onde
não entra) no projeto.

MCP não é um formato de dado nem um tradutor semântico entre protocolos — é um protocolo
para expor *ferramentas* e *recursos* de um sistema a um **cliente de IA** (Claude
Desktop, Cursor, outro agente) de forma padronizada, no mesmo papel que uma API REST ou
uma CLI já cumprem: uma porta de entrada (*driving adapter*), não uma peça de
compreensão semântica. Quem já faz o trabalho de "o SLM entender melhor as entidades" é o
Nível 2 (`SemanticAnalyzerPort`/`OllamaAnalyzer` + RAG, ADR-0014) — isso não muda com MCP.

Verificação no próprio projeto (antes de decidir): `docs/plano_refatoracao_v3.md` já
desenha um servidor MCP desde a concepção original do DKRT, na Parte II (arquitetura),
como **adaptador de entrada** no mesmo nível que REST API e CLI:

```
DRIVING ADAPTERS (entrada)
REST API (FastAPI) · CLI (Typer) · MCP Server
```

com um arquivo previsto em `interfaces/mcp/server.py` ("expõe auditoria como ferramenta
MCP"), e `docs/analizy/analise.md` já registra a intenção de expor operações do domínio
como ferramentas nomeadas (`dkrt_orchestrate`, `dkrt_query_entities`,
`dkrt_interpret_nl`, na concepção original do DKRT de propósito mais amplo) com testes de
integração cobrindo o protocolo JSON-RPC. `docs/fases/fase-00-planejamento-e-escopo.md`
lista isso como requisito (R4: "Protocolos NGSI-v2 e MCP") desde a Fase 0.

Ou seja: isto não é escopo novo — é escopo já previsto que ainda não tinha ganhado uma
fase de implementação própria. Conferido no código real: não existe ainda
`interfaces/mcp/` em `src/auditor/`, e nenhum dos `fase1.spec.md`–`fase9.spec.md` (as
specs que efetivamente guiaram o que foi construído até agora) cobre MCP — ele aparece só
nos documentos de planejamento de mais alto nível. Busca na internet não encontrou nenhum
servidor MCP publicado para FIWARE Orion/NGSI — construir este seria, até onde se pôde
verificar, uma contribuição original para a monografia, não a réplica de algo já existente.

## Decisão

Adotar o servidor MCP como um terceiro adaptador de entrada, ao lado de REST API e CLI,
expondo os casos de uso de aplicação já existentes como ferramentas MCP — não como
tradução do protocolo NGSI, e não como substituto de nenhuma peça do Nível 1/Nível 2.

Ferramentas propostas (adaptando os nomes do DKRT original ao recorte atual de auditor,
mantendo a convenção de nomenclatura do projeto — verbos precisos, sem
`process`/`handle`/`manage` genéricos):

| Ferramenta MCP | Caso de uso de aplicação por trás | Efeito |
|---|---|---|
| `run_audit` | `RunAuditUseCase` | Dispara uma auditoria (tenant + tipo de entidade) — mesma operação por trás de `POST /audits` (REST) e do comando `audit` (CLI) |
| `get_audit_report` | Leitura via `AuditRepositoryPort` (hoje servida direto pelo router `audits.py`) | Consulta o relatório de um run já concluído |
| `query_schema_catalog` | `SchemaCatalogPort`/`sync_catalog.py` | Consulta qual Smart Data Model está associado a um `entity_type` |

Implementação prevista em `src/auditor/interfaces/mcp/server.py`, reaproveitando
diretamente os casos de uso de `application/use_cases/` já testados — o servidor MCP não
duplica lógica de negócio, apenas adapta a chamada (mesmo padrão já usado por
`interfaces/rest/routers/` e `interfaces/cli/main.py`). Requer o SDK oficial de MCP para
Python (`mcp`), a ser adicionado a `pyproject.toml`.

Esta ADR registra a decisão de **fazer** o servidor MCP e **como ele se encaixa**
arquiteturalmente; o detalhamento contrato-por-contrato (dado/quando/então, no mesmo
formato das fases anteriores) fica para uma spec própria (`fase11.spec.md`), da mesma
forma que a Fase 7 teve a sua.

## Alternativas consideradas

- **Não implementar MCP, manter só REST + CLI** — descartada: contradiz o requisito R4 já
  registrado desde a Fase 0 e a intenção documentada em `analise.md`; também descartaria
  sem necessidade um ângulo de contribuição original (nenhum servidor MCP para FIWARE
  Orion foi encontrado publicado).
- **Usar MCP como camada interna entre os agentes e o Orion** (expor `get_entity`,
  `query_entities` do Context Broker como ferramentas MCP consumidas pelos próprios
  agentes do sistema) — considerada e não adotada agora: o `ContextBrokerPort`/
  `OrionAdapter` já cumprem esse papel internamente, testados e em uso; introduzir MCP
  nesse ponto trocaria uma integração já madura por uma nova, sem um cliente externo que
  precise consumir Orion via MCP hoje. Fica registrada como extensão possível se surgir
  essa necessidade (ex.: um agente de terceiros querendo operar o Orion do usuário
  diretamente), não como decisão tomada agora.
- **Reaproveitar os nomes de ferramenta originais do DKRT verbatim** (`dkrt_orchestrate`,
  `dkrt_query_entities`, `dkrt_interpret_nl`) — descartada: o domínio atual é o de
  auditoria de conformidade, não o de orquestração ampla de comandos sobre o Orion que o
  DKRT original propunha; os nomes acima (`run_audit`, `get_audit_report`,
  `query_schema_catalog`) descrevem o que o sistema de fato faz hoje.

## Consequências

**Positivas:**
- Qualquer cliente MCP (Claude Desktop, Cursor, outro agente) passa a poder rodar e
  consultar auditorias em linguagem natural sem integração REST/CLI sob medida — a mesma
  proposta central do DKRT ("interpreta comandos em linguagem natural... via CLI, RAG e
  MCP"), na camada de interface.
- Cumpre um requisito (R4) registrado desde a Fase 0 que ainda não tinha sido endereçado.
- Ângulo de contribuição original para a monografia: nenhum servidor MCP para FIWARE
  Orion/Smart Data Models foi encontrado publicado até a data desta ADR.

**Negativas / trade-offs aceitos:**
- Novo adaptador de entrada para manter e testar (testes de integração cobrindo o
  protocolo JSON-RPC, conforme já previsto em `analise.md`) — mais uma superfície exposta
  ao lado de REST e CLI, com sua própria superfície de autenticação/autorização a definir
  (a Parte VI, seção 3.8, do plano geral já lista JWT + filtro por tenant no repositório
  como exigência transversal; o servidor MCP herda essa exigência, não fica isento dela).
- Escopo detalhado (contratos dado/quando/então, casos de teste) ainda não foi escrito —
  esta ADR decide o *que* e *onde*, não o *como* linha a linha; isso fica para
  `fase11.spec.md`.
- Dependência nova (`mcp`, SDK oficial) a avaliar quanto à maturidade/estabilidade da
  versão disponível no momento da implementação.
