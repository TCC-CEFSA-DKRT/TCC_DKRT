# ADR-0021: Três ambientes AWS (dev em EC2, homologação e produção em Lambda) e pipeline por GitHub Actions com OIDC e build único

Data: 2026-11-03
Status: Aceito (substitui parcialmente a ADR-0018)

## Contexto

O Manual de Gestão de Código e Entrega (v1.3, seções 3 e 4) define três ambientes —
DEV, HOMOLOGAÇÃO e PRODUÇÃO — e o caminho de uma mudança até eles. O repositório estava
longe disso: um único workflow (`terraform-and-audit.yml`) ainda apontava para o ambiente
`academy` descontinuado (ADR-0018), não havia CI de testes, não havia deploy de aplicação, o
ambiente `homolog` era uma stack EC2 diferente da produção (então homologar não validava o que
iria para produção) e `environments/dev` não existia. O usuário decidiu: os três ambientes
ficam na AWS (nada de AWS Academy/Lab), numa conta única com prefixo por ambiente.

## Decisão

1. **Arquitetura por ambiente.** `dev` = uma instância EC2 que roda a imagem `selfhosted`
   (API e worker no mesmo processo), RDS Postgres, S3 website; `homolog` e `production` =
   a mesma stack Lambda + ALB + CloudFront/S3 da ADR-0017, extraída para o módulo
   `modules/stack_lambda` e chamada por `environments/homolog` e `environments/production`
   (que só diferem em parâmetros: Multi-AZ, retenção, snapshot final, prefixo). Homologar passa
   a validar exatamente a arquitetura que vai para produção.
2. **Conta e estado.** Uma conta AWS, prefixos `auditor-dev`, `auditor-homolog`, `auditor-prod`.
   O stack `infra/terraform/bootstrap` (state local, aplicado uma vez à mão) cria o bucket de
   state, a tabela de lock, o bucket de artefatos, o provedor OIDC do GitHub e os papéis IAM.
   Cada ambiente tem uma chave de state própria.
3. **Credenciais: OIDC, sem chave de acesso.** Os workflows assumem papéis IAM por OIDC
   (`aws-actions/configure-aws-credentials` com `role-to-assume`). Cada papel só pode ser
   assumido pelo GitHub Environment correspondente (`dev`, `homologacao`, `producao`,
   `infra-<ambiente>`), então a aprovação do Environment é também um controle de acesso à AWS.
   O projeto Portal_mobilemed usa chaves estáticas por Environment; foi descartado aqui porque
   chaves de longa duração vazam e exigem rotação, e a configuração OIDC não custa mais.
4. **Gatilhos (manual v1.3).** DEV: `workflow_dispatch` com a branch escolhida. HOMOLOGAÇÃO:
   tag `vX.Y.Z-rc.N` em commit de `release/X.Y.Z` que contém a `main`. PRODUÇÃO: tag `vX.Y.Z`
   na `main`, com conteúdo idêntico (árvore) à `-rc` mais recente, e aprovação manual do
   Environment `producao`. Terraform: `infra-apply.yml`, manual, com plano salvo e aprovado.
5. **Build único.** A imagem Lambda e o build do frontend são produzidos na homologação.
   A produção promove os mesmos bits: a imagem é copiada de repositório ECR com `docker
   pull/tag/push` e o digest é conferido; o frontend vem do bucket de artefatos, só trocando
   a URL da API. Nada é reconstruído para produção. O artefato do DEV nunca é promovido.
6. **Migrações antes do tráfego.** A função Lambda `admin` recebe a imagem nova primeiro e roda
   `alembic upgrade head`; só se `exit_code == 0` API e workers são atualizados. No DEV, o mesmo
   papel é feito pelo script `auditor-deploy migrate` na instância (via SSM).
7. **Terraform e a imagem.** As funções Lambda sobem com uma imagem `bootstrap` e têm
   `ignore_changes = [image_uri]`: quem troca a versão é o pipeline de deploy, não o `apply`.

## Alternativas consideradas

- **Todos os ambientes em EC2** (reaproveitar a ADR-0018): mais simples de escrever, mas
  homologação deixaria de validar produção. Recusada.
- **Contas separadas por ambiente:** melhor isolamento; custo operacional maior para um TCC.
  A estrutura de prefixos permite migrar depois, trocando apenas o ARN dos papéis.
- **Chaves de acesso por Environment** (como no Portal_mobilemed): mais comum no repositório
  irmão, menos seguro. Recusada.

## Consequências

- Boas: homologação ≡ produção; mesmo artefato nos dois; segredos de longa duração inexistentes;
  deploy de produção exige aprovação humana; rollback de produção por workflow (`rollback-producao.yml`).
- Custos assumidos: Multi-AZ e NAT/VPC endpoints em produção custam mesmo ocioso; homologação
  pode desligar NAT e Ollama (`start_ollama.sh`/`stop_ollama.sh`). O `dev` mantém uma EC2 ligada.
- Pendências conhecidas: o código Terraform foi formatado (`fmt`) e conferido estruturalmente, mas
  **`terraform validate/plan/apply` ainda não foi executado** por falta de provedores/conta no
  ambiente de autoria; o primeiro `plan` real pode apontar ajustes. A tolerância do Orion no
  runner (3 cenários DKRT) depende de `ORION_URL`. O manual v1.3 e a Fig. 2 devem ganhar uma
  linha dizendo que a homologação é Lambda (antes: EC2).
