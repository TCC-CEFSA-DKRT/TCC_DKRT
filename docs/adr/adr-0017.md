# ADR-0017: API e worker de produção migram de EC2 para Lambda (imagem de contêiner) atrás de um ALB, com CloudFront/S3, Parameter Store e VPC endpoints

Data: 2026-09-11
Status: Aceito

## Contexto

Ao auditar a Fase 9 (`.cursor/specs/fase9.spec.md`) contra sua própria "Definição
de pronto" (seção 9), foi encontrado um gap real: o security group da API
(`modules/network`, `aws_security_group.api`) já abre a porta 443 desde a Fase 9,
mas nenhum listener HTTPS/certificado ACM jamais existiu — a API EC2 só respondia
HTTP puro na porta 8000. A seção 5 do spec original é explícita sobre TLS ser
esperado.

Perguntado como resolver esse gap especificamente, o usuário respondeu para
seguir a arquitetura do produto já desenhada anteriormente:
*"Pra resolver isso siga a arquitetura do produto, que é o diagrama ja feito
anteriormente"* — referência a `docs/design/implantacao-aws.html`, um artefato de
design já produzido nesta sessão (antes deste ADR) especificando uma topologia de
produção bem mais ampla que "só adicionar um ALB": Lambda (API + worker) atrás de
ALB, CloudFront + S3 para o frontend, Parameter Store no lugar de Secrets Manager
para os segredos do próprio projeto, e VPC Interface Endpoints.

Isso é uma mudança de escopo muito maior que o gap original (TLS/ALB), então dois
pontos foram levados de volta ao usuário antes de implementar:

1. **Tamanho da mudança** — implementar só o ALB/TLS (fiel ao gap encontrado) ou o
   diagrama inteiro (fiel à resposta do usuário, mas uma migração de compute bem
   maior)? Resposta: **"Tudo de uma vez (Recomendado p/ fidelidade ao diagrama)"**.
2. **Bloqueio técnico real, encontrado ao desenhar o Lambda do worker**: o Nível 2
   (Fase 7) carrega `sentence-transformers`/`torch` em tempo de execução
   (`infrastructure/rag/embedder.py`, usado por `PgVectorRetriever.retrieve()` a
   cada `RunAuditUseCase._build_report()`) — essas duas dependências sozinhas
   excedem o limite de 250 MB (descomprimido) de um pacote `.zip` de Lambda. Duas
   saídas possíveis: trocar o embedder por um serviço gerenciado (ex. Bedrock
   Embeddings), ou empacotar como imagem de contêiner (limite de 10 GB). Resposta:
   **"Lambda via imagem de contêiner (Recomendado)"** — mantém o código/modelo de
   embeddings já testado nas Fases 6/7 sem nenhuma mudança de comportamento.

## Decisão

Migrar API e worker de produção (`environments/production` — **não** a Academy,
que continua 100% EC2, ver seção "Escopo" abaixo) de EC2 para **AWS Lambda,
empacotado como imagem de contêiner**, atrás de um Application Load Balancer com
HTTPS/ACM, com as demais peças do diagrama:

- **Compute**: uma única imagem de contêiner (`Dockerfile` na raiz do repo, base
  `public.ecr.aws/lambda/python:3.11`), três funções Lambda (`api`, `worker`,
  `worker-dlq`) trocando só `image_config.command` — três handlers novos em
  `src/auditor/interfaces/aws_lambda/` (`api_handler.py` via Mangum,
  `worker_handler.py`/`worker_dlq_handler.py` consumindo `event["Records"]`
  diretamente em vez de `AuditWorker.consume()`, reportando falha parcial de lote
  via `batchItemFailures`). Ollama **continua em EC2** (`modules/compute`),
  inalterado — decisão própria (ADR-0013), não uma limitação do Lambda.
- **ALB**: `target_type = "lambda"` (sem API Gateway), listener HTTPS 443 com
  certificado ACM (validação DNS via Route53) + redirect 80→443
  (`modules/edge_alb`, novo).
- **Frontend**: CloudFront + S3 com Origin Access Control, também com ACM (em
  `us-east-1`, exigência da própria AWS para certificados usados por CloudFront —
  `modules/frontend_delivery`, novo).
- **Segredos do projeto** (credenciais do Orion, chave JWT): Parameter Store
  (SSM SecureString, chave gerenciada pela AWS — sem custo de KMS próprio) no
  lugar do Secrets Manager comum (`modules/secrets`, que a Academy continua
  usando) — `modules/parameter_store`, novo.
- **Rede**: NAT gateway opcional (`enable_nat_gateway`, default `false` —
  zero mudança para a Academy) + VPC Interface Endpoints para SQS e SSM
  (`modules/vpc_endpoints`, novo) — o Lambda de produção fica dentro da VPC (para
  alcançar RDS e Ollama por IP privado) e precisa de uma rota de saída para o
  Orion do cliente (endereço arbitrário na internet) e o Secrets Manager (senha
  gerenciada do RDS) — nenhum dos dois é coberto por endpoint de VPC, fiel ao
  diagrama, que só lista SQS+Parameter Store como endpoints.

Além disso, dois gaps reais foram encontrados e corrigidos como pré-requisito
funcional desta migração (sem eles o Lambda não funcionaria de fato, mesmo com
toda a infraestrutura correta):

- **`container.get_job_queue()` sempre retornava `LocalJobQueue()`**, mesmo com
  `QUEUE_BACKEND=sqs`/`SQS_QUEUE_URL` já escritos no ambiente pelo `user_data` do
  EC2 desde a Fase 9 (`api.sh.tftpl`/`worker.sh.tftpl`) — nenhum `AuditJob`
  chegava de fato à fila SQS real. Corrigido: `Settings` ganhou
  `queue_backend`/`sqs_queue_url`/`sqs_dead_letter_queue_url`, e
  `get_job_queue()` agora troca de implementação conforme `queue_backend`.
- **`interfaces/rest/app.py` sempre iniciava `AuditWorker`/`CatalogSyncScheduler`
  como tasks em background**, um anti-padrão para Lambda (o ambiente de execução
  pode congelar/retomar o processo entre invocações). `create_app()` ganhou
  `start_background_workers: bool = True` — `api_handler.py` passa `False`.

## Escopo

Esta migração é **só para `environments/production`**. `environments/academy`
(onde este TCC de fato roda) permanece inteiramente EC2, sem nenhuma alteração de
comportamento — todas as mudanças em módulos compartilhados
(`modules/network.enable_nat_gateway`, `modules/compute.provision_api/
provision_worker`) têm default que preserva exatamente o plano atual da Academy
(ver `moved` blocks em `modules/compute/main.tf`, que evitam destroy+recreate das
instâncias EC2 da Academy só por causa da mudança de `aws_instance.api` para
`aws_instance.api[0]`).

`environments/production` já carregava, antes deste ADR, a nota "Nunca aplicado
neste projeto: escrito e validado localmente (terraform-config-inspect/hcl2), não
contra uma conta AWS de produção real" — isso continua verdadeiro depois desta
mudança, e o CI (`.github/workflows/terraform-and-audit.yml`) continua validando
só a Academy. A validação desta mudança foi: `python-hcl2` (sintaxe de todos os
`.tf`, novos e modificados) + um script de verificação cruzada (todo `module.X.Y`
referenciado existe e é declarado; toda variável passada a um módulo existe nele;
toda variável obrigatória de cada módulo é fornecida) — não substitui um
`terraform validate`/`plan` real contra uma conta AWS (`terraform` não pôde ser
instalado neste ambiente de execução: `releases.hashicorp.com` bloqueado pelo
proxy de saída).

## Alternativas consideradas

- **Só o ALB/TLS, sem migrar compute** — mais fiel ao gap original encontrado
  (TLS ausente), bem menor. Descartada pela resposta explícita do usuário: seguir
  o diagrama já desenhado, "tudo de uma vez".
- **Trocar o embedder por um serviço gerenciado (ex. Bedrock Embeddings) para
  caber num Lambda `.zip`** — evitaria o Dockerfile/ECR. Descartada pelo usuário:
  imagem de contêiner preserva o código/modelo de embeddings já testado nas Fases
  6/7 sem reabrir essa decisão.
- **API Gateway na frente do Lambda da API** — padrão mais comum, mas o diagrama
  já especifica ALB com `target_type=lambda` diretamente (sem API Gateway) —
  seguido à risca por fidelidade à decisão já tomada no design.
- **Domínio/certificado autoassinado ou fictício** para não depender de um
  domínio real — descartada: fabricar um domínio de mentira para o ACM validar
  seria menos honesto que declarar `domain_name`/`route53_zone_id` como variáveis
  sem default, documentando que este projeto (AWS Academy Learner Lab) nunca
  registrou um domínio próprio (ver `modules/edge_alb`, `modules/frontend_delivery`).

## Consequências

**Positivas:**
- Fecha o gap real de TLS ausente da Fase 9 com HTTPS de verdade (ACM), não um
  workaround.
- Corrige dois bugs pré-existentes que impediriam a fila SQS de funcionar de fato
  em produção (`get_job_queue()`) e que eram um anti-padrão para Lambda (tasks de
  background sempre ativas).
- Nenhuma mudança de comportamento na Academy — validado por inspeção de todas as
  variáveis/defaults tocadas.
- Custo de segredo menor (Parameter Store SecureString com chave gerenciada pela
  AWS, sem os ~US$0,40/segredo/mês do Secrets Manager nem um KMS Key próprio).

**Negativas / trade-offs aceitos:**
- **`CatalogSyncScheduler` deixa de rodar automaticamente em produção** —
  `start_background_workers=False` desliga as duas tasks de fundo (worker E
  scheduler) juntas, porque `_make_lifespan()` as trata como uma unidade. O
  catálogo de Smart Data Models em produção passa a depender de um gatilho
  explícito (`audit catalog sync`, CLI, ou um passo de deploy que o chame) —
  gap conhecido, **não resolvido por este ADR**, deixado para um trabalho futuro
  (ex.: uma quarta função Lambda + EventBridge Scheduler, o mesmo padrão dos
  outros três handlers).
- **Cold start**: a primeira invocação de cada função Lambda após ociosidade
  carrega o container inteiro (para o worker, incluindo `sentence-transformers`/
  `torch`) — trade-off aceito explicitamente pelo diagrama
  (`docs/design/implantacao-aws.html`, card "Compute": "cold-start trade-off
  aceito"), sem provisioned concurrency (custo adicional não justificado para um
  protótipo de TCC).
- **Exige um domínio real registrado e delegado a um Route53 hosted zone antes de
  um `terraform apply` real** (`var.domain_name`/`var.route53_zone_id` em
  `modules/edge_alb`/`modules/frontend_delivery`, sem default) — este projeto
  nunca teve um domínio próprio; permanece um passo manual fora do Terraform.
- **`interfaces/worker/main.py` continua ausente** — gap pré-existente, encontrado
  (não introduzido) durante este trabalho: `worker.sh.tftpl` (EC2) referencia
  `python -m auditor.interfaces.worker.main`, que não existe em lugar nenhum do
  repositório. Como o worker de produção migra para Lambda (que não usa esse
  entrypoint), este ADR **não corrige** esse gap — ele continua afetando só o
  worker EC2 da Academy, fora do escopo desta migração.
- Nenhuma validação `terraform validate`/`plan` real foi possível (ver seção
  "Escopo") — o mesmo limite que já existia para o restante de
  `environments/production` antes deste ADR.

## Notas

Um gap menor, sem relação direta com Lambda, encontrado e corrigido de passagem
ao tocar um módulo vizinho: `environments/production/main.tf` nunca resolvia uma
AMI com driver NVIDIA/CUDA para o Ollama (só `environments/academy/main.tf` fazia
isso, desde a ADR-0015) — a GPU do `ollama_instance_type` default
(`g4dn.xlarge`) ficaria ociosa e o Ollama rodaria em CPU sem avisar, exatamente o
cenário que a ADR-0015 já havia identificado como risco. Corrigido (mesmo
`data "aws_ami" "ollama_gpu"` da Academy, agora também em
`environments/production/main.tf`).

Consequência mecânica (não um gap descoberto) de `aws_instance.api`/
`aws_instance.worker` passarem a usar `count` (`provision_api`/
`provision_worker`, acima): os outputs de `modules/compute/outputs.tf` que
indexavam esses dois recursos diretamente precisaram trocar para
`try(...[0]..., null)` — mesmo padrão já usado ali para `ollama_instance_id`/
`ollama_private_ip` e em `modules/database/outputs.tf`.
