# ADR-0010: Coexistência de STH-Comet (legado) e QuantumLeap (novo) para dados históricos

Data: 2026-08-15
Status: Aceito

## Contexto

A ADR-0003 decidiu QuantumLeap como o backend de dados históricos para o projeto.
Na prática, porém, QuantumLeap é o sucessor do STH-Comet dentro do FIWARE — e
projetos legados que este sistema também precisa atender ainda têm dados e
subscrições vivendo no STH-Comet. Substituir o STH-Comet nesses projetos está
fora do escopo controlável por este sistema; ele precisa conviver com os dois
simultaneamente, não escolher um só.

## Decisão

- **Escrita (novas subscrições/persistência):** sempre vai para o QuantumLeap.
  Nenhuma subscrição nova é criada apontando para o STH-Comet — ele só existe
  para servir dados que já estavam lá antes desta decisão.
- **Leitura e remoção de histórico existente:** o backend usado depende do
  contexto, com uma regra determinística:
  1. Se o chamador informar o backend explicitamente (`backend="quantumleap"`
     ou `backend="sth_comet"`), usa exatamente esse.
  2. Caso não informe, tenta primeiro o QuantumLeap; se não encontrar dado
     para aquela entidade/atributo, cai para o STH-Comet.
- Isso é implementado por um novo componente, `HistoricalBackendResolver`
  (`services/historical_backend_resolver.py`), que orquestra dois clientes
  concretos (`QuantumLeapClient`, `SthCometClient`) atrás da mesma interface
  já definida na ADR-0003 (`HistoricalDataClient`).
- **Limitação assumida:** remover histórico sem informar o backend explicitamente
  exige informar o atributo (`attribute`) — não existe, em nenhum dos dois
  backends, uma forma de perguntar "esta entidade tem histórico de *algo*?"
  sem apontar um atributo específico primeiro. Sem `backend` nem `attribute`,
  o resolvedor levanta erro explícito em vez de adivinhar.

## Alternativas consideradas

- **Roteamento por tipo de entidade ou Fiware-ServicePath (mapeamento estático)**
  — mais previsível e não depende de round-trip extra ao QuantumLeap antes de
  decidir, mas exige manter uma lista de "quais tipos/paths são legados"
  atualizada manualmente; descartada a pedido do responsável pelo projeto, que
  preferiu resolução automática por tentativa (QuantumLeap primeiro).
- **Escrever em ambos os backends simultaneamente** — evitaria a necessidade de
  resolver "onde está" na hora de ler; descartada porque contraria a decisão
  explícita de que toda escrita nova é só no QuantumLeap (não faz sentido
  persistir dado novo também no backend que está sendo descontinuado).

## Consequências

**Positivas:**
- Projetos legados continuam funcionando sem migração forçada de dados.
- Novas subscrições já nascem no backend recomendado pela comunidade FIWARE.
- A escolha de backend fica isolada em uma única camada (`HistoricalBackendResolver`),
  então nenhum código de agente/handler precisa saber que dois backends existem.

**Negativas / trade-offs aceitos:**
- Uma consulta sem backend explícito pode custar duas chamadas HTTP (QuantumLeap
  vazio + STH-Comet) em vez de uma, quando o dado é legado.
- Remoção de histórico sem backend explícito exige o atributo — não há uma
  forma de "apagar tudo de uma entidade em qualquer um dos dois backends"
  numa única chamada sem essa informação.
- `SubscribeHandler` (ADR-0008) e `HistoricalBackendResolver` compartilham o
  domínio de dados históricos mas não trocam informação entre si hoje — o
  handler só sabe criar subscrição nova (sempre QuantumLeap); nada aqui ainda
  registra "esta entidade passou a ter histórico novo no QuantumLeap a partir
  de tal data", o que poderia otimizar a ordem de tentativa no resolvedor no
  futuro (ideia para trabalho futuro, não implementada).
