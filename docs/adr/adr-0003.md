# ADR-0003: QuantumLeap como componente de persistência histórica

Data: 2026-08-09
Status: Aceito

## Contexto

O backend de referência do projeto (diagrama original + coleção Postman fornecidos) especifica STH-Comet como componente de série histórica, alimentado por uma subscription do Orion e persistindo em uma segunda base MongoDB ("Historical"). O projeto ainda não implementa nenhum cliente de histórico — este é trabalho planejado, não código existente — o que torna este o momento correto para avaliar STH-Comet contra a alternativa mais atual do ecossistema FIWARE antes de escrever qualquer linha de código.

## Decisão

Adotar **QuantumLeap** como componente de persistência e consulta histórica, em vez de STH-Comet.

Isso implica mudanças em múltiplos componentes, não apenas na nomenclatura do cliente:
- Banco de dados: **CrateDB** (SQL distribuído, voltado a IoT/série temporal) substitui a segunda base MongoDB planejada.
- `docker-compose.yml`: adiciona `crate-db` (portas 4200/4300) e `quantumleap` (porta 8668, `CRATE_HOST=crate-db`).
- Cliente de histórico (`quantumleap_client.py`) é implementado atrás de uma interface abstrata `HistoricalDataClient`, para isolar `HistoryAgent`/`IntentRouter` da escolha de backend.
- `SubscribeAgent` notifica `http://quantumleap:8668/v2/notify` em vez do endpoint do STH-Comet.

## Alternativas consideradas

- **STH-Comet, conforme o diagrama de referência original** — descartada como escolha final, mas registrada como alternativa avaliada: é o componente que o diagrama do projeto especifica, e tem mais tutoriais legados em português, o que reduz fricção de aprendizado. Motivo do descarte: está em modo de manutenção pela comunidade FIWARE, com menor atividade de desenvolvimento e suporte que QuantumLeap; para um projeto com 12 meses de vida útil (o TCC), o risco de depender de um componente pouco mantido pesa mais que o benefício de aderência estrita ao diagrama original.

## Consequências

**Positivas:**
- Componente ativamente mantido pela comunidade FIWARE, menor risco de bugs não documentados ao longo dos 12 meses do projeto.
- API de consulta mais próxima da sintaxe nativa NGSI (v2/LD), com suporte a agregações (`aggrMethod`/`aggrPeriod`) que o STH-Comet não oferece da mesma forma.
- Caminho aberto para integração com Grafana (visualização de série temporal), útil para demonstrações futuras — não obrigatório, mas disponível.
- Compatibilidade futura com NGSI-LD, caso o projeto evolua para além do NGSI-v2 atual.

**Negativas / trade-offs aceitos:**
- Desvio do diagrama de referência original fornecido ao grupo — precisa ser justificado explicitamente na monografia (este ADR serve como base para essa justificativa).
- Introduz CrateDB como uma peça de infraestrutura adicional (distinta do MongoDB já usado por Orion), aumentando a superfície de operação do `docker-compose.yml`.
- Menos tutoriais em português disponíveis, comparado a STH-Comet.
