# ADR-0000: Orquestração determinística com SLM classificador, em vez de agente aberto (tool-use) com RAG/fine-tuning

Data: 2026-08-15
Status: Aceito

## Contexto

A concepção original do projeto previa um modo mais próximo de um agente
autônomo: o usuário descreve um pedido em linguagem natural, o SLM tem a
documentação do NGSI-v2 à disposição (via RAG) e decide sozinho — sem
vocabulário pré-definido — qual chamada HTTP formar e executar contra o
Orion Context Broker. Nesse modelo, atualizar a documentação bastaria para
o sistema passar a suportar novos recursos, sem alterar código Python.

A arquitetura efetivamente implementada (ADR-0001 a ADR-0009) é diferente:
o SLM tem uma única responsabilidade — classificar o texto do usuário em um
`ChatIntent` de formato fixo, escolhido entre um vocabulário fechado de seis
operações (`query, list, create, update, delete, subscribe`). A partir daí,
toda decisão de execução, formação de payload NGSI e verificação de
resultado é código determinístico, sem envolvimento do modelo. O projeto já
possui infraestrutura de RAG (`services/rag_retrieve.py`,
`knowledge/raw/fiware_ngsi_v2.md`), mas ela hoje só é usada num comando
secundário (`dkrt-tools ask --rag`), nunca no fluxo principal do chat.

Essa divergência entre a concepção original e a implementação levantou a
dúvida: vale a pena migrar para o modo mais aberto, especialmente
considerando que o modelo usado é um SLM local (Qwen2.5/phi-2 via
Ollama/llama.cpp), não um modelo de fronteira, e que fine-tuning poderia, em
tese, compensar essa diferença de capacidade.

## Decisão

Mantém-se a orquestração determinística com SLM classificador como única
arquitetura em produção. O modo mais agentic (SLM decidindo livremente qual
chamada HTTP formar, informado por RAG) não será implementado nesta fase do
projeto, pelos motivos detalhados abaixo. A infraestrutura de RAG
permanece como está — disponível, mas não incorporada ao caminho de decisão
principal.

## Alternativas consideradas

- **Agente aberto com RAG (SLM forma a chamada HTTP diretamente, informado
  pela documentação NGSI-v2)** — descartada nesta fase. Um SLM local tem taxa
  de erro de formato/tool-calling mensuravelmente maior que modelos de
  fronteira, mesmo com contexto via RAG; isso desloca para o modelo uma
  responsabilidade (formar corretamente uma requisição contra um sistema com
  estado real) que hoje é garantida por código testável.

- **Agente aberto com fine-tuning (SLM treinado especificamente em
  exemplos NGSI-v2, sem restringir a um vocabulário fixo)** — descartada.
  Fine-tuning reduz erro de formato/domínio, mas não o elimina — continua
  sendo inferência probabilística, sujeita a alucinação de endpoint ou
  interpretação errada de ambiguidade semântica no pedido do usuário (ex.:
  "apague os sensores inativos" exige um critério que o modelo pode
  inferir incorretamente mesmo formando uma chamada HTTP tecnicamente
  válida). Além disso, fine-tuning contraria o próprio objetivo que motivou
  considerar essa arquitetura: gravar conhecimento nos pesos do modelo
  significa que uma atualização da documentação do NGSI-v2 só se reflete no
  comportamento do sistema após novo treinamento — reintroduzindo, de outra
  forma, o mesmo acoplamento entre "mudança de capacidade" e "trabalho
  manual" que se buscava eliminar ao tirar isso do código Python.

- **Híbrido: RAG pesado + fine-tuning leve, com validador determinístico e
  loop de verificação obrigatório antes de qualquer execução** — considerada
  a alternativa mais coerente com o objetivo original, caso o projeto venha
  a evoluir nessa direção no futuro. Não implementada nesta fase por
  representar escopo novo, não previsto nas ADRs 0001–0009, e por exigir
  desenho cuidadoso do validador (allowlist de paths/métodos NGSI aceitos)
  antes de ser seguro habilitar.

## Consequências

**Positivas:**
- O espaço de erro do SLM fica limitado a escolher entre seis rótulos
  fixos, não a formar uma chamada HTTP arbitrária — o restante do sistema
  (formação de payload, execução, verificação) é testável e determinístico,
  independente de qual modelo (ou provedor) está classificando.
- Trocar de SLM (inclusive por um mais capaz no futuro) é uma mudança
  localizada: nenhuma camada abaixo do classificador precisa saber qual
  modelo gerou o `ChatIntent`.
- Ações mutáveis (`create/update/delete/subscribe`) sempre passam pelo loop
  de verificação (ADR-0002) antes de serem consideradas concluídas,
  independentemente da capacidade do modelo — a robustez do sistema vem da
  arquitetura de verificação, não da qualidade do SLM.

**Negativas / trade-offs aceitos:**
- Suportar um recurso novo do NGSI-v2 (ex.: um novo tipo de filtro de
  consulta) ainda exige alterar código Python (o vocabulário fixo de
  operações e os handlers), não apenas atualizar a documentação em
  `knowledge/raw/` — o objetivo original de acoplamento zero entre
  documentação e comportamento não foi alcançado nesta fase.
- A infraestrutura de RAG já construída (`RagRetriever`, base de
  conhecimento) permanece subutilizada — funcional, mas fora do caminho
  principal de decisão do chat.
- Um modo mais agentic, se vier a ser explorado futuramente (ex.: como
  extensão experimental para fins de comparação na monografia), exigirá
  desenho de segurança adicional (validador determinístico de
  paths/métodos permitidos) antes de poder coexistir com o caminho atual
  sem risco para dados reais no Context Broker.
